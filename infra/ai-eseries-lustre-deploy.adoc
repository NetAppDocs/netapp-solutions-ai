= Lustre with NetApp E-Series Storage - Deploy the Solution
:hardbreaks:
:nofooter:
:icons: font
:linkattrs:
:imagesdir: ../media/

[.lead]
This section describes the high-level deployment workflow for Lustre with NetApp E-Series Storage. Detailed procedures, inventory examples, and command references are in the NetApp ansible-lustre collection and deployment templates on GitHub.

== Prerequisites

Complete the following before starting deployment:

. Confirm that the servers, E-Series arrays, and network fabric appear in IMT for the *E-Series Lustre* solution.
+
link:https://imt.netapp.com/imt/#welcome[NetApp Interoperability Matrix Tool^]

. Select the building block type (base, MDT+OST, or OST-only).
. Select the fabric (InfiniBand or RoCE) and E-Series platform (EF80 or EF600).
. Select the drive layout (TLC with RAID 6 volume groups, or QLC with DDP).
. Prepare an Ansible control node with the required collections installed.

For requirements, see link:ai-eseries-lustre-requirements.html[Technical requirements]. For architecture context, see link:ai-eseries-lustre-architecture.html[Solution architecture].

NOTE: A pre-deployment inventory checklist will be published on GitHub. Until then, use the deployment template README in the ansible-lustre collection and the sizing guidance in link:ai-eseries-lustre-validation.html[Validation and sizing].

== Deployment overview

The deployment workflow consists of seven phases. Each phase maps to playbooks in the link:https://github.com/NetApp/ansible-lustre/tree/release/1.0.0[ansible-lustre collection^].

. Prepare hardware and network
. Configure E-Series arrays
. Prepare server operating systems
. Customize the Ansible inventory
. Deploy the Lustre HA cluster
. Deploy Lustre clients
. Verify the deployment

NOTE: IP addresses, hostnames, interface names, and volume sizing in the deployment templates are examples. Modify all inventory files for the environment before running any playbook.

== Phase 1: Prepare hardware and network

. Rack and cable two OSS/MDS servers and two E-Series arrays per building block.
. Cable the backend NVMe-oF network between servers and arrays according to the platform topology (six HCAs per node on EF80, four HCAs per node on EF600). Both topologies are validated; additional HCAs increase NVMe-oF paths to maximize array performance. The cabling figure below shows the EF80 six-HCA layout; EF600 uses four HCAs per node with the same Node A to array *a* ports and Node B to array *b* ports rule described in link:ai-eseries-lustre-requirements.html#_backend_nvme_of[Backend (NVMe-oF)^].

_EF80 six-HCA backend cabling (RoCE or InfiniBand)_

image:lustre-ef80-6hca-cabling.png["EF80 six-HCA backend NVMe-oF cabling between two OSS/MDS server nodes and two EF80 arrays"]

. Cable the frontend LNet fabric (IPoIB or RoCE) for Lustre client and inter-node communication. LNet uses four frontend interfaces (i1 and i4 HCAs) in each configuration. The backend cabling figure above does not show frontend connections. For preferred Lustre target placement across nodes and arrays, see link:ai-eseries-lustre-requirements.html#_primary_building_block_volume_distribution[target distribution^] in link:ai-eseries-lustre-requirements.html[Technical requirements].
. Configure out-of-band management for server BMCs and array management ports.
. Configure the RoCE fabric for lossless operation (PFC) when using RoCE.

== Phase 2: Configure E-Series arrays

Configure array management addresses, NVMe-oF port addressing, and initial SANtricity settings.

. Install the link:https://github.com/NetApp/ansible-lustre[ansible-lustre^] and link:https://github.com/NetApp/ansible-santricity[ansible-santricity^] collections on the Ansible control node.
. Copy the deployment template inventory for the fabric and platform.
. Update array management IP addresses and NVMe-oF port configuration in the `host_vars` files for each array.
. Run the storage array configuration playbook:

[source,bash]
----
ansible-playbook -i <inventory_path>/lustre_inventory.yml \
  configure_storage_array_playbook.yml
----

This playbook provisions volume groups or DDP pools and creates volumes for MGS, MDT, and OST targets according to the inventory.

== Phase 3: Prepare server operating systems

Prepare each OSS/MDS node with the supported operating system, kernel, NVIDIA networking packages, and NetApp-built Lustre packages.

. Install the operating system and enable required repositories (see IMT).
. Run the OS preparation and NVIDIA package playbooks from the deployment template:

[source,bash]
----
ansible-playbook -i <inventory_path>/lustre_inventory.yml \
  deploy_lustre_os/deploy_lustre_os_playbook.yml

ansible-playbook -i <inventory_path>/lustre_inventory.yml \
  deploy_nvidia_packages/deploy_nvidia_packages_playbook.yml
----

. Install NetApp-built Lustre packages from link:https://github.com/NetApp/netapp-lustre[netapp-lustre^].

== Phase 4: Customize the Ansible inventory

Copy and customize the deployment template inventory for the site. For field-level inventory guidance, see the deployment template README in the ansible-lustre collection.

=== Deployment templates

Start from the template that matches the fabric and platform:

* *InfiniBand, EF80:* link:https://github.com/NetApp/ansible-lustre/tree/release/1.0.0/getting_started/lustre_deployment_template/building_blocks/IB_H2_IB_DAC_A2_EF80/lustre_building_block_cluster_1[IB_H2_IB_DAC_A2_EF80/lustre_building_block_cluster_1^]
* *RoCE, EF80 (six-HCA):* The `ROCE_H2_6HCA_RoCE_DAC_A2_EF80` template is not yet published in ansible-lustre `release/1.0.0`. Use the internal template as a reference until it is available in the collection.

=== Key inventory files

Customize at minimum `lustre_inventory.yml`, `host_vars` for each server and array, and `group_vars` for MGS, MDS, OSS, HA cluster, and E-Series storage settings. Set building block type by including or excluding MGS and MDS resource groups in the inventory. For an OST-only additional building block, include OSS resource groups only and register targets against the existing MGS using `mgsnode=`.

== Phase 5: Deploy the Lustre HA cluster

Run the main Lustre deployment playbook:

[source,bash]
----
ansible-playbook -i <inventory_path>/lustre_inventory.yml \
  lustre_playbook.yml
----

This playbook configures NVMe-oF host connectivity, formats and mounts Lustre targets, configures LNet, applies performance tuning, and configures Pacemaker HA resources. For role tags and incremental execution options, see the lustre role documentation in the collection.

== Phase 6: Deploy Lustre clients

Deploy Lustre clients on compute nodes that require file system access.

. Build Lustre client packages from NetApp Lustre SRPMs in link:https://github.com/NetApp/netapp-lustre[netapp-lustre^] for a client operating system listed in the link:https://wiki.whamcloud.com/display/PUB/Lustre+Support+Matrix[Lustre Support Matrix^], or use the optional `lustre_client` Ansible role from the ansible-lustre collection.
. Configure LNet on each client to match the server frontend fabric (handled by `lustre_client` when using Ansible).
. Mount the file system using the MGS NIDs and file system name from the deployment (also managed by `lustre_client` when using Ansible).

Example mount command (replace NIDs and file system name with site-specific values):

[source,bash]
----
mount -t lustre <nid1>@o2ib,<nid2>@o2ib,...:/<fsname> /mnt/<fsname>
----

== Phase 7: Verify the deployment

Verify that the deployment completed successfully:

. Confirm that all Pacemaker resources are started on the expected nodes.
. Confirm that all MDT and OST targets are mounted and visible in `mount` output.
. Run `lfs df -h` from a client or server node to confirm file system capacity.
. Write and read test files from a Lustre client.
. Test HA failover by stopping a target resource on one node and confirming that it starts on the partner node.

== Expand the file system

To add capacity or metadata performance, deploy an additional building block and register it against the existing MGS:

. Deploy a new building block (MDT+OST or OST-only) using the same workflow above.
. Assign globally unique MDT and OST indices in the inventory.
. Set the `mgsnode=` parameter to reference the existing MGS NIDs.
. Ensure the new building block uses the same `fsname` and LNet fabric as the existing file system.

See link:ai-eseries-lustre-architecture.html[Solution architecture] for scaling rules and link:ai-eseries-lustre-validation.html[Validation and sizing] for guidance on when to add each building block type.

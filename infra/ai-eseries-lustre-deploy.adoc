Deploy Lustre with NetApp E-Series Storage by racking and cabling hardware, preparing servers and arrays, customizing the Ansible inventory, and running the NetApp `ansible-lustre` playbooks. Detailed inventory examples and command references are in the collection and deployment templates on GitHub.

== Prerequisites

This page assumes you have already sized the solution, verified interoperability, and acquired the equipment for the planned building blocks.

Before you start the deployment, ensure the following:

* You followed the sizing and building-block guidance in link:ai-eseries-lustre-sizing.html[Sizing guidance] and selected hardware that matches link:ai-eseries-lustre-hw.html[Hardware components].
* You confirmed that the server, HCA, E-Series, operating system, Lustre, SANtricity OS, and DOCA-OFED combination is listed for *E-Series Lustre* in the link:https://imt.netapp.com/imt/#welcome[NetApp Interoperability Matrix Tool^].
* All OSS/MDS server nodes and E-Series arrays for the planned building blocks are on site and ready to rack.
* You have credentials and network access for server BMCs, array management ports, and the host that will serve as the Ansible control node.

NOTE: NetApp supports deploying the Lustre HA cluster and Lustre clients with the link:https://github.com/NetApp/ansible-lustre[ansible-lustre^] collection. Do not configure Lustre targets, LNet, NVMe-oF host connectivity, or Pacemaker resources manually.

[[phase-prepare-hardware]]
== Phase 1: Rack and cable the hardware

Rack the Lustre servers and E-Series storage arrays, then cable the physical infrastructure for each building block.

. Rack and cable all Lustre servers and E-Series arrays according to the building block topology.
. For each EF80 array, cable controller A port 4a to controller B port 4a, and controller A port 4b to controller B port 4b. These dedicated connections provide inter-controller mirroring and are not used for host traffic. EF600 arrays do not require external inter-controller mirroring cables. See link:https://docs.netapp.com/us-en/e-series/install-hw-ef50-ef80/install-cable.html#step-1-cable-the-inter-controller-mirroring-connections[Cable the EF50 and EF80 inter-controller mirroring connections^].
. Cable the backend NVMe-oF network between servers and arrays according to the platform topology. The following figure shows the EF80 six-HCA layout.
+
.EF80 six-HCA backend cabling (RoCE or InfiniBand)
image:eseries-lustre-ef80-6hca-cabling.png["EF80 six-HCA backend NVMe-oF cabling between two OSS/MDS server nodes and two EF80 arrays"]
. Connect the four frontend LNet interfaces (the i1 and i4 HCAs) on each Lustre server and the Lustre clients to the dedicated InfiniBand or RoCE switch fabric.
. When using RoCE, configure the fabric for lossless operation with priority flow control (PFC).

For HCA counts, path requirements, and MTU guidance, see link:ai-eseries-lustre-hw.html[Hardware components].

[[phase-prepare-servers-arrays]]
== Phase 2: Prepare servers and arrays

Configure management access and base settings on each E-Series array and Lustre server.

=== Prepare E-Series arrays

. Configure the management interface on each controller and verify that SANtricity System Manager is reachable.
. Set the array name and administrative credentials that the Ansible inventory will use.
. Confirm that the array is in an optimal state and that all drives are present and reporting correctly.

For instructions on configuring the management connection, see the link:https://docs.netapp.com/us-en/e-series/[E-Series documentation^].

=== Prepare Lustre servers

. Configure the baseboard management controller (BMC) on each server for out-of-band access, and set the UEFI system settings for maximum performance.
. Install a supported operating system (RHEL or Rocky Linux), then configure the host name and the management network port.
. Prepare all firmware and software packages to meet the requirements for the *E-Series Lustre* solution, as described in link:ai-eseries-lustre-sw.html[Software components].

[[phase-prepare-control-node]]
== Phase 3: Prepare the Ansible control node

Designate a virtual or physical Linux system with management network access to all Lustre servers and E-Series arrays to be the Ansible control node.

The following steps use Ubuntu 24.04. For instructions for another Linux distribution, see the link:https://docs.ansible.com/ansible/latest/installation_guide/intro_installation.html[Ansible installation documentation^].

. Install Python, pip, and the Python virtual environment package:
+
[source,console]
----
sudo apt-get install python3 python3-pip python3-setuptools python3-venv
----
. Create and activate a Python virtual environment:
+
[source,console]
----
python3 -m venv ~/pyenv
source ~/pyenv/bin/activate
----
. Install Ansible and the required Python packages in the activated virtual environment:
+
[source,console]
----
pip install "ansible-core>=2.19" cryptography jinja2 ipaddr netaddr \
  passlib pyyaml resolvelib
----
. Install the NetApp E-Series Lustre Ansible collection. The collection installation also installs its dependent collections, including the SANtricity and Host collections:
+
[source,console]
----
ansible-galaxy collection install netapp_eseries.lustre
----
. Verify the installed Ansible, Python, and collection versions:
+
[source,console]
----
ansible --version
python3 --version
ansible-galaxy collection list netapp_eseries.lustre
----
. Configure passwordless SSH from the control node to each Lustre server. Replace `<ip_or_hostname>` with the management IP address or host name of a server:
+
[source,console]
----
ssh-keygen
ssh-copy-id <ip_or_hostname>
----
+
Repeat `ssh-copy-id` for each Lustre server.

NOTE: Do not configure passwordless SSH to the E-Series arrays. Ansible manages the arrays through the SANtricity Web Services API by using the credentials defined in the inventory.

[[phase-customize-inventory]]
== Phase 4: Customize the Ansible inventory

Create a working copy of the `building_blocks` deployment template that preserves its directory structure. Keep the selected inventory under its fabric and platform directory, and retain the shared `playbooks` directory and `passwords.yml` file at the root of `building_blocks`. Customize the inventory to populate the servers, arrays, and building blocks for your site. Use the table in this section for field-level inventory guidance.

=== Deployment templates

Start from the template that matches the site's network fabric and E-Series array platform:

* *InfiniBand, EF80:* link:https://github.com/NetApp/ansible-lustre/tree/release/1.0.0/getting_started/lustre_deployment_template/building_blocks/IB_H2_IB_DAC_A2_EF80/lustre_building_block_cluster_1[IB_H2_IB_DAC_A2_EF80/lustre_building_block_cluster_1^]
* *RoCE, EF80:* link:https://github.com/NetApp/ansible-lustre/tree/release/1.0.0/getting_started/lustre_deployment_template/building_blocks/ROCE_H2_ROCE_DAC_A2_EF80/lustre_building_block_cluster_1[ROCE_H2_ROCE_DAC_A2_EF80/lustre_building_block_cluster_1^]

Populate this file and encrypt it with Ansible Vault before deployment, or override the values securely at runtime with `--extra-vars`. Do not commit plaintext credentials to source control.

NOTE: IP addresses, hostnames, interface names, and volume sizing in the deployment templates are examples. Modify all inventory files for the environment before running any playbook.

[[phase-deploy-ha]]
== Phase 5: Deploy the Lustre HA cluster with Ansible

Prepare the operating system, install the NVIDIA DOCA-OFED software, then run the main Ansible playbook to provision storage, configure connectivity, and build the HA cluster.

. From the `building_blocks/playbooks` directory in your working copy, prepare the operating system on the Lustre servers. Replace `<inventory_path>` with the path to your customized inventory directory:
+
[source,console]
----
ansible-playbook -i <inventory_path>/lustre_inventory.yml deploy_lustre_os/deploy_lustre_os_playbook.yml
----
. Install NVIDIA DOCA-OFED on each Lustre server. Build the kernel modules against the kernel that the previous step installed. Follow the procedure for your kernel in link:https://networking-docs.nvidia.com/doca/archive/3-2-3/doca-host-installation-and-upgrade#id-(3.2.3-Jun_Oct25LTSU3)DOCA-HostInstallationandUpgrade-DOCAExtraPackageanddoca-kernel-support[NVIDIA DOCA-Host installation and upgrade^].
+
[%collapsible]
.Example DOCA-OFED installation on RHEL or Rocky Linux
====
. Install the DOCA host repository package and refresh the package cache. Replace `<doca_host_package>` with the DOCA host package for your operating system and architecture:
+
[source,console]
----
dnf install -y wget tar
wget https://www.mellanox.com/downloads/DOCA/<doca_host_package>.rpm
rpm -i <doca_host_package>.rpm
dnf clean all
dnf makecache
----
. Build the DOCA kernel modules for the running kernel. The script prints the path of the package it creates:
+
[source,console]
----
dnf install -y doca-extra
/opt/mellanox/doca/tools/doca-kernel-support
----
. Install the kernel module repository package that the script created, then refresh the package cache. Replace `<doca_kernel_repo>` with the path from the previous step:
+
[source,console]
----
rpm -Uvh <doca_kernel_repo>.rpm
dnf makecache
----
. Install the DOCA-OFED user space, kernel, and NVMe packages. Replace `<kernel_version>` with the running kernel version:
+
[source,console]
----
dnf install -y doca-ofed-userspace
dnf install -y --disablerepo=doca doca-kernel-<kernel_version>
dnf install -y kmod-mlnx-nvme
----
====

. Run the main deployment playbook:
+
[source,console]
----
ansible-playbook -i <inventory_path>/lustre_inventory.yml lustre_playbook.yml
----
+
NOTE: Adjust `--forks` for the size of the deployment to control how many hosts Ansible configures in parallel. For example, add `--forks 20` for a larger cluster.

This playbook provisions E-Series volume groups or DDP pools and volumes, configures NVMe-oF host connectivity, formats and mounts the Lustre targets, configures LNet, applies performance tuning, and configures the Pacemaker HA resources. For role tags and incremental execution options, see the lustre role documentation in the collection.

NOTE: A deployment with one building block forms a two-node Pacemaker cluster. Node A is given an extra vote in the case of failover. To achieve quorum in a two-node cluster, consider configuring a qdevice. When a deployment contains multiple building blocks, each building block contributes a two-node server pair to the larger Pacemaker cluster, up to the documented cluster limit. Review the fencing and quorum configuration in the HA administration guide so the cluster can safely recover targets during a node failure.

[[phase-deploy-clients]]
== Phase 6: Deploy Lustre clients with Ansible

Deploy Lustre clients on any system that requires file system access by customizing the client deployment template and running the client playbook.

. Select a compatible client operating system and kernel from the link:https://wiki.whamcloud.com/display/PUB/Lustre+Support+Matrix[Lustre Support Matrix^]. Build and install the Lustre client packages for that kernel from link:https://github.com/NetApp/netapp-lustre[netapp-lustre^] if they are not already installed.
. Create a working copy of the `clients` template directory, including its shared `passwords.yml` file, and select the template that matches your fabric:
+
* *InfiniBand:* link:https://github.com/NetApp/ansible-lustre/tree/release/1.0.0/getting_started/lustre_deployment_template/clients/IB_lustre_cluster_clients[IB_lustre_cluster_clients^]
* *RoCE:* link:https://github.com/NetApp/ansible-lustre/tree/release/1.0.0/getting_started/lustre_deployment_template/clients/ROCE_lustre_cluster_clients[ROCE_lustre_cluster_clients^]
. Customize `lustre_client_inventory.yml`, `host_vars`, and `group_vars` for your clients by setting the site-specific values in the following table. Line references point to the RoCE client template files in the `ansible-lustre` `release/1.0.0` tag; the InfiniBand client template uses the same variables except where noted.
+
[cols="2,3,4,2,4",options="header"]
|===
| Field | Ansible variable | Template file (`release/1.0.0`) | Scope | Notes

| Client hosts
| `lustre_clients`
| link:{client-tmpl}/lustre_client_inventory.yml#L4[lustre_client_inventory.yml#L4^]
| Per client
| List each client host name.

| Client SSH user and become password
| `ssh_client_user` / `ssh_client_become_pass`
| link:https://github.com/NetApp/ansible-lustre/blob/release/1.0.0/getting_started/lustre_deployment_template/clients/passwords.yml#L2[passwords.yml#L2^]
| Cluster-wide
| Set the become password only if the SSH user is not `root`.

| LNet interfaces
| `eseries_lustre_lnet`
| link:{client-tmpl}/group_vars/all.yml#L7[group_vars/all.yml#L7^]
| Cluster-wide
| Client-side LNet interface names (values at L13).

| Mount MGS NIDs
| `lustre_client_mounts.mgsnode`
| link:{client-tmpl}/group_vars/all.yml#L17[group_vars/all.yml#L17^]
| Cluster-wide
| MGS NIDs used to mount the file system (values at L20).

| File system name
| `lustre_client_mounts.fsname`
| link:{client-tmpl}/group_vars/all.yml#L21[group_vars/all.yml#L21^]
| Cluster-wide
| Must match the cluster `fsname`.

| Mount point
| `lustre_client_mounts.mount_point`
| link:{client-tmpl}/group_vars/all.yml#L22[group_vars/all.yml#L22^]
| Cluster-wide
| Client mount directory.

| Client management IP
| `ansible_host`
| link:{client-tmpl}/host_vars/client_01.yml#L4[host_vars/client_01.yml#L4^]
| Repeat per client
| One `host_vars/client_NN.yml` file per client.

| Storage fabric interfaces
| `eseries_roce_interfaces`
| link:{client-tmpl}/host_vars/client_01.yml#L10[host_vars/client_01.yml#L10^]
| Repeat per client
| Frontend interface addresses (values at L15). The InfiniBand template uses `eseries_ipoib_interfaces` here.
|===
+
NOTE: Repeat for each client. Create one `host_vars/client_NN.yml` file for each client and add the corresponding host to `lustre_client_inventory.yml`. Populate the shared `clients/passwords.yml` file and encrypt it with Ansible Vault before running the client playbook.

. Run the client playbook from the client template directory:
+
[source,console]
----
ansible-playbook -i lustre_client_inventory.yml lustre_client_playbook.yml
----

The client playbook configures the client network interfaces and LNet, and can create a persistent systemd mount unit for the file system.

[[phase-verify]]
== Phase 7: Verify the deployment

Verify that the deployment completed successfully before you place the file system in production.

. From a Lustre server, confirm that all Pacemaker resources are started on the expected nodes:
+
[source,cli]
----
pcs status
----

. From a Lustre client, confirm that all MDT and OST targets are mounted and visible:
+
[source,cli]
----
mount -t lustre
----

. From a Lustre client, confirm the file system capacity:
+
[source,cli]
----
lfs df -h
----

For performance validation with IOR, mdtest, and fio, see link:ai-eseries-lustre-sizing.html[Sizing guidance].

For controlled target migration or HA failover testing, follow the procedures in the link:https://github.com/NetApp/ansible-lustre/blob/release/1.0.0/roles/lustre/docs/ha_user_guide.md[HA user guide^].

== Expand the file system

To add capacity or metadata performance, extend your existing inventory with an additional building block. Do not create a separate inventory for the new building block. The playbook automatically assigns unique MDT and OST indices and registers the new targets against the existing MGS.

. Add the new building block hosts, arrays, and resource groups (MDT+OST or OST-only) to the same inventory and `host_vars` / `group_vars` you used for the original deployment.
. Rerun the main deployment playbook against the updated inventory.

See link:ai-eseries-lustre-architecture.html[Solution architecture] for scaling rules and link:ai-eseries-lustre-sizing.html[Sizing guidance] for guidance on when to add each building block type.

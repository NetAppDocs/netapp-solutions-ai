This section lists the technical requirements for servers, NetApp E-Series storage, networking, and software for the Lustre with NetApp E-Series Storage solution.

== Server requirements

The solution uses a bring-your-own-server (BYOS) model. Each building block requires two OSS/MDS server nodes that meet or exceed the following specifications.

.Server requirements (per OSS/MDS node)
|===
| Component | Requirement

| Quantity
| 2 nodes per building block

| Operating system
| See IMT (search *E-Series Lustre*)

| Lustre version
| See IMT (search *E-Series Lustre*)

| CPU
| AMD EPYC or Intel Xeon, 32 cores or higher

| Memory
| 256 GB DDR5 (minimum)

| Network HCAs
| Platform-dependent (see <<platform-connectivity,Platform connectivity>>)

| Boot drives
| 2× drives in RAID 1 (software or hardware RAID recommended)

| Local storage
| None required; all Lustre data resides on E-Series arrays via NVMe-oF
|===

NetApp validated the solution using Lenovo ThinkSystem SR665 V3 servers. Equivalent servers from other vendors are supported when they meet these requirements and appear in IMT for the *E-Series Lustre* solution.

=== Drive layout (24 drives per array)

Each EF80 array in a base building block uses all twenty-four NVMe drive slots:

* 4× drives in RAID 1 for MGS/MDT storage (shared volume group or DDP allocation)
* 10× drives in RAID 6 for OST storage (first OST pool)
* 10× drives in RAID 6 for OST storage (second OST pool)

This layout applies when using TLC drives with traditional volume groups. When using QLC drives, provision a single Dynamic Disk Pool across all twenty-four drives and create RAID 1 volume groups inside the pool for MGS and MDT volumes.

== Other E-Series platforms

NetApp EF600 and other EF-Series models are supported with the same building block profiles. EF600 uses sixteen OSTs per building block (EF80 uses thirty-two); MGS and MDT counts are the same. Connectivity, port counts, and maximum performance differ by platform. Consult IMT and the EF-Series datasheet for model-specific requirements.

== Storage pool selection: TLC vs QLC

Choose the E-Series pool type based on the NVMe drive type in the arrays:

* *TLC drives:* Use *RAID 6 volume groups* for OST volumes. Use *RAID 1 volume groups* for MGS and MDT volumes.
* *QLC drives:* Use *Dynamic Disk Pools (DDP)* for the shared drive pool. Create RAID 1 volume groups inside the DDP for MGS and MDT volumes. Allocate OST volumes from the DDP.

Use a 32 KB segment size for all volume types regardless of pool type.

== Network requirements

=== Backend (NVMe-oF)

* NVMe/InfiniBand or NVMe/RoCE between each OSS/MDS node and each E-Series array
* MTU 9000 on NVMe/RoCE backend interfaces (typical)
* Eight paths per array on EF80 (four per array on EF600)

=== Frontend (LNet)

* IPoIB or RoCE for LNet (`@o2ib` network type)
* MTU 9216 on RoCE frontend interfaces (typical)
* Multi-rail LNet recommended when four frontend ports are available (EF80: i1 and i4 HCAs, both ports)
* Lossless RoCE (PFC) recommended on RoCE fabrics

=== Management

* Out-of-band management network for server BMCs and array management ports
* Dedicated Corosync network or shared frontend fabric (site-dependent)

== Lustre target format parameters

Lustre targets use the `ldiskfs` backend file system. Configure `mkfs.lustre` options to align with E-Series volume geometry.

=== OST format options

.OST mkfs.lustre options (typical)
|===
| Parameter | Value | Rationale

| `-E stride=8`
| 32 KB segment ÷ 4 KB block
| Aligns to E-Series 32 KB segment size

| `-E stripe-width=64`
| 8 stride × 8 data drives
| Aligns to RAID 6 full stripe (8 data drives in 10-drive RAID 6)

| `-i 1048576`
| 1 MiB inode spacing
| Lustre default for OSTs larger than 8 TiB

| `-I 512`
| 512-byte inodes
| Sufficient for OST extended attribute storage
|===

Example Ansible inventory setting:

[source,yaml]
----
mkfsoptions: "-E stride=8,stripe-width=64 -i 1048576 -I 512"
----

The Ansible collection applies format options during deployment. Customize options in the inventory when RAID geometry differs from the standard building block layout.

== Client requirements

Lustre clients require:

* A supported client operating system and kernel version for the deployed Lustre release (see the link:https://wiki.whamcloud.com/display/PUB/Lustre+Support+Matrix[Lustre Support Matrix^])
* Connectivity to the LNet frontend fabric
* Lustre client packages built from NetApp Lustre source RPMs (SRPMs) in link:https://github.com/NetApp/netapp-lustre[netapp-lustre^] (recommended), or deployment via the optional `lustre_client` Ansible role

Clients are deployed independently of building blocks. See link:ai-eseries-lustre-deploy.html[Deploy the solution] for client deployment steps.

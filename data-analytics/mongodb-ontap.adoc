This reference architecture presents an end-to-end solution for efficiently deploying and protecting virtualized MongoDB on NetApp storage controllers. The solution combines NetApp storage technology with VMware vSphere: a scale-out NetApp AFF array hosts the MongoDB virtual machines and databases. The architecture delivers very high performance with consistently low latency and excellent inline storage efficiency. NetApp SnapCenter backup software creates instant, space-efficient copies of the MongoDB environment for testing, development, QA, backup, and recovery. The reference architecture also demonstrates remote replication to NetApp ONTAP in the cloud and describes two customer use cases.

== Introduction

MongoDB is a popular open-source, scale-out NoSQL database. It powers modern data lake applications that require low latency for reads and writes, high availability, and advanced data management. Key use cases for MongoDB include real-time analytics, product catalogs, content management, and mobile applications.

This reference architecture describes a validated, end-to-end design for deploying a virtualized, scale-out MongoDB NoSQL database on NetApp storage controllers and VMware vSphere. In this solution, the scale-out NetApp All Flash FAS (AFF) array hosts the MongoDB virtual machines (VMs) and databases. Backup and disaster recovery services are provided by NetApp ONTAP software-defined storage in Amazon AWS. The report also covers two customer use cases.

The NetApp solution offers the following key benefits for deploying mission-critical MongoDB applications:

* Predictable high performance with consistent low latency compared with direct-attached storage, providing excellent response time for the most demanding analytics applications built on MongoDB.
* Inline efficiency from inline deduplication and compression, which minimizes the flash storage that MongoDB requires.
* Instant, space-efficient, and cost-efficient database cloning for rapid setup of dev/test or QA environments without buying new storage.
* Backup and recovery based on space-efficient NetApp Snapshot technology, and remote replication to the cloud.
* Scalability from the scale-up and scale-out AFF array, which scales storage modularly with MongoDB.
* Nondisruptive operations with high availability, delivering maximum uptime and consistent performance, specifically during drive failure.
* Deployment of MongoDB in a heterogeneous environment, providing flexibility and additional cost savings.
* Single-interface management by using Snap Creator with the MongoDB plug-in.

== Solution design

This section describes the MongoDB architecture, including its components and layout, followed by the validated architecture and the storage architecture used in this solution.

=== MongoDB architecture

Sharding, or horizontal scaling, divides a dataset and distributes it across multiple servers, or shards. Each shard is an independent database, and together the shards make up a single logical database. The following figure shows how the shards of a collection can be spread across multiple servers.

.Shards spread across multiple servers
image:mongodb-ontap-002.png[Diagram showing a collection divided into shards that are spread across multiple servers.]

Shards store the data. In a production sharded cluster, each shard is a replica set, which provides high availability and data consistency.

Query routers, or `mongos` instances, interface with client applications and direct operations to the appropriate shard or shards. A client sends requests to a `mongos`, which routes the operations to the shards and returns the results to the client. A sharded cluster can contain more than one `mongos` to divide the client request load, and most sharded clusters have more than one.

Configuration servers (config servers) store the cluster's metadata, which maps the cluster's dataset to the shards. The query router uses this metadata to target operations to specific shards, as the following figure shows.

.Query routers (mongos instances) using metadata to route data to shards
image:mongodb-ontap-003.png[Diagram showing mongos query routers using config server metadata to route operations to shards.]

[NOTE]
Starting in MongoDB 3.2, config servers for sharded clusters can be deployed as a replica set, which must run the WiredTiger storage engine. MongoDB 3.4 removed mirrored config servers, so current MongoDB versions require config servers to be deployed as a replica set.

=== Validated architecture

This solution uses a MongoDB sharded cluster that is virtualized on VMware vSphere 6. Following the MongoDB recommendation for a production setup, we deployed a sharded cluster of two shards during testing. Each shard holds a subset of a collection's data, and each shard is a replica set. The cluster also uses three config servers and two query routers (`mongos` instances), and MongoDB is configured with the WiredTiger storage engine. WiredTiger manages how data is stored, both in memory and on disk, and creates the data files in the `--dbpath` or `storage.dbPath` location.

For more information, see the MongoDB documentation for link:https://www.mongodb.com/docs/manual/core/wiredtiger/[WiredTiger Storage Engine^] and link:https://docs.mongodb.org/manual/core/sharded-cluster-architectures-production/[Production Cluster Architecture^].

== Solution validation

This section describes how we validated the end-to-end solution, focusing on the key benefits listed in the introduction.

=== Build the MongoDB sharded cluster

Deploying the MongoDB sharded cluster involves the following tasks:

. Check the mounted partitions for the MongoDB database.
. Check and start the shard cluster members, create the required folders, and set the required permissions. The `mongod` process starts with the default ports (27018 and 28018), or you can specify different ports.
. Verify that the config server folders, such as the log path (`/mongodb/data/configdb`) and the database path (`/data/db`), exist and have `mongodb` user permissions (700). Verify that the `mongod` process is running in fork mode on the correct port (27019).
. Start the `mongos` process on the MongoDB router or application server, and verify that it is listening on port 27017.
. Initiate the replica set by connecting to the MongoDB shard primary server from the MongoDB application server.
. Check the replica set status from a shard member.
. Add a shard from the application server. Then try to add the same shard from another application server. You should get a message that the shard already exists.
. Check the sharding status from the application server.
. Add another shard to the existing sharded cluster.
. Check the sharded cluster status by running the `sh.status()` command from the MongoDB application server.

For the detailed MongoDB steps, see <<Appendix: MongoDB operations>>.

=== Back up and restore with NetApp Snap Creator

This solution uses the NetApp Snap Creator framework and space-efficient NetApp Snapshot technology to back up, restore, and clone the virtualized MongoDB database environment. In our testing, NetApp Snapshot backups of the complete environment took less than one minute, and restoring the NetApp volumes that hosted the MongoDB database also took less than one minute.

MongoDB uses the WiredTiger storage engine in this solution. For our testing, we configured Snap Creator to perform the following operations:

. Stop the balancer.
. Perform an `fsync` and lock, if necessary.
. Make NetApp Snapshot copies of all volumes used in the configuration.
. Unlock the databases for writes, if necessary.
. Restart the balancer.

[NOTE]
The WiredTiger storage engine does not require an `fsync` and write lock on every shard, and it does not require you to unlock the databases afterward. If you use the MMAPv1 storage engine, you must perform an `fsync` and lock on every shard for writes, and then unlock them. MongoDB 4.2 and later do not include MMAPv1.

==== Snap Creator backup

Snap Creator is a flexible framework that can run MongoDB-specific quiesce and unquiesce scripts before and after it creates the NetApp Snapshot backup. The size of the database does not affect the NetApp Snapshot backup, which takes only seconds to create.

We followed this procedure to configure Snap Creator for our testing:

. Install the Snap Creator server in the Snap Creator VM.
. Install the Snap Creator agent on the MongoDB router or application server. The Snap Creator server communicates with the MongoDB database through the Snap Creator agent, which communicates with MongoDB as a client. The same mechanism runs the Python scripts for the quiesce and unquiesce operations on the MongoDB database.
. In the Snap Creator UI, create the MongoDB profile and configure the following settings:
.. Set the plug-in type to *None*.
.. Configure the Snap Creator agent on one of the MongoDB application servers.
.. Select the transport *https* with port 443.
.. Select the storage virtual machine (SVM, formerly Vserver) IP and provide the SVM user name and password.
.. Include the four MongoDB database volumes (primary and secondary):
+
* `n1_mdbdata_p_01`
* `n1_mdbdata_s_02`
* `n2_mdbdata_p_02`
* `n2_mdbdata_s_01`
.. Provide the Snapshot copy name and indicate the policies. The default value is monthly, but you can customize the policies to fit your requirements:
+
* Daily: 30
* Hourly: 24
* Weekly: 7
* Monthly: 12
.. Provide the application quiesce command:
+
----
APP_QUIESCE_CMD01=/usr/bin/python2.7 /usr/local/bin/wait-for-cleared-locks.py mdb-ms-1 27017
----
.. Provide the application unquiesce command:
+
----
APP_UNQUIESCE_CMD01=/usr/bin/python2.7 /usr/local/bin/start-balancer.py mdb-ms-1 27017
----
.. Provide the pre-exit command:
+
----
PRE_EXIT_CMD01=/usr/bin/python2.7 /usr/local/bin/start-balancer.py mdb-ms-1 27017
----

The following figure shows the Snap Creator backup operation for the MongoDB database.

==== Snap Creator restore

As a database grows, backing it up and restoring it becomes harder. NetApp Snapshot technology provides the simplest and most efficient way to back up and restore a distributed database of any size. When backups are based on Snapshot copies, restoring a large database composed of multiple shards depends more on the time needed to stop and start the database processes than on restoring the data itself. Restoring from a Snapshot backup often takes only seconds, or minutes at most.

The following example from our testing removes the `c7` collection, stops all `mongod` processes across all shards, unmounts the `/data` file systems, restores the volumes by using Snap Creator, remounts the file systems, removes the lock files, and restarts all processes:

. Before the restore, check the database and its documents from one of the application servers. The `c7` collection in the `db7` database held 144,569,144 documents at the time of the backup. Drop the collection to simulate data loss, and confirm that the count is 0:
+
----
mongos> use db7;
mongos> db.c7.count();
144569144
mongos> db.c7.drop();
true
mongos> db.c7.count();
0
----
. Stop the `mongod` process on the first shard's replica set members (`mdb-srv-1`, `mdb-srv-10`, and `mdb-srv-11`) by using the init script or the `kill` command, and unmount the database volume. For example, on `mdb-srv-1`:
+
----
[mongodb@mdb-srv-1 ~]$ pkill mongod
[root@mdb-srv-1 ~]# umount /data
----
. Stop the `mongod` process on the second shard's replica set members (`mdb-srv-2`, `mdb-srv-20`, and `mdb-srv-21`) and unmount their database volumes in the same way.
. Delete the existing virtual disks (the MongoDB database volumes) from the VMs of both shards, including the primary and secondary servers.
. Restore all database volumes by using Snap Creator, one volume at a time. The following figure shows one volume (`n1_mdbdata_p_01`). You must restore `n1_mdbdata_s_02`, `n2_mdbdata_p_02`, and `n2_mdbdata_s_01` as well.
+
.Restoring a MongoDB database volume with Snap Creator
image:mongodb-ontap-006.png[Snap Creator restore of the n1_mdbdata_p_01 volume from a Snapshot copy.]
. Reconnect the restored database volumes as existing disks to the primary and secondary servers of each shard.
. Mount the volumes.
. Remove the `mongod.lock` file from the mounted MongoDB database volumes.
. Start the `mongod` process on the shard servers, and verify that the `mongod` ports (27018 and 28018) are listening. For example, on `mdb-srv-1`:
+
----
[root@mdb-srv-1 ~]# mount /data
[mongodb@mdb-srv-1 ~]$ cd /data/db_wt/
[mongodb@mdb-srv-1 db_wt]$ rm -f mongod.lock
[mongodb@mdb-srv-1 db_wt]$ mongod --replSet shard1/mdb-srv-10,mdb-srv-11 --journal --rest --shardsvr --fork --storageEngine wiredTiger --dbpath /data/db_wt --logpath /mongodb/data/mongod.log --directoryperdb
----
. Repeat the procedure on `mdb-srv-10`, `mdb-srv-11`, `mdb-srv-2`, `mdb-srv-20`, and `mdb-srv-21`. Mount the restored volume, remove the `mongod.lock` file, and start the `mongod` process for the replica set.
. Check the sharding status and the document counts in the restored database. The `c7` collection returns to 144,569,144 documents:
+
----
mongos> use db7
mongos> show collections;
c7
mongos> db.c7.count();
144569144
----

This example demonstrates that you can restore a MongoDB database by using Snap Creator with NetApp Snapshot copies and NetApp SnapRestore technology.

=== MongoDB cloning for dev/test and QA with Snap Creator

Snap Creator enables you to build preproduction or development environments from existing production NetApp Snapshot backups. With NetApp FlexClone technology, you can present volumes that contain Snapshot copies to any clone host. This approach lets you build dev/test environments quickly without doubling the storage you need. FlexClone clones provide a fast, scalable, and efficient way to deliver dev/test environments on demand.

The following example clones all databases across all shard servers into new shard servers. In this example, the operating system volumes are also cloned.

. Create the Snap Creator profile for the database volumes and for the operating system volumes.
+
image:mongodb-ontap-007.png[Snap Creator profile for the database and operating system volumes.]
. In Snap Creator, create FlexClone volumes for the operating system and database volumes from a specific Snapshot copy.
. Create a datastore on the VMware servers that includes the cloned operating system and database volumes.
+
image:mongodb-ontap-008.png[VMware datastore created from a cloned operating system volume.]
+
image:mongodb-ontap-009.png[VMware datastore created from a cloned database volume.]
. Create the cloned VM from the datastore, based on the `.vmx` file:
.. Select the datastore that you created in the previous step.
.. Find the `.vmx` file.
.. Register the VM.
.. Name the cloned VM in the format `cl_<old VM name>`.
.. Select the VMware cluster and server to finish creating the cloned VM.
. The cloned (newly registered) VM accesses the database `.vmdk` file from another cloned database volume. Verify that the `.vmdk` file is identified as an existing disk. If it is not, in the cloned VM, select *Edit > Settings > Remove disk > Confirm*. Make sure that you do not remove the disk from the repository.
. Remove the `.lck-<16 alphanumeric characters>` files from the cloned database volume. Mount the cloned volume in the VMware or Linux server and remove the `.lck` files:
+
----
[root@stlrx300s8-9:/vmfs/volumes/24631f70-b7e80cce/mdb-srv-1] ls -la
-rwxrwxr-x 1 root root 84 Dec 18 14:41 .lck-be54694500000000
-rwxrwxr-x 1 root root 84 Dec 18 2015 .lck-be546a4500000000
-rw------- 1 root root 1088516510720 Dec 18 14:41 mdb-srv-1-flat.vmdk
-rw------- 1 root root 475 Nov 22 17:51 mdb-srv-1.vmdk
[root@stlrx300s8-9:/vmfs/volumes/24631f70-b7e80cce/mdb-srv-1] rm -fr .lck-be546*
----
. Before powering on any cloned VM, attach its network adapter to an isolated port group that cannot reach the production MongoDB hosts.
. Power on the cloned VMs and use the VM console to assign new IP addresses and update `/etc/hosts` for all cloned members before starting MongoDB. Retain the host names only within the isolated clone network.
. Restart the MongoDB config, application, and replica set or sharding servers with the new IP addresses from the cloned VMs.

This procedure creates a working cloned copy of the production MongoDB database. The clone is isolated, so you can use it for writes, troubleshooting, development, or test. Because its storage is based on FlexClone technology, the process uses no additional storage.

. Configure and initialize a SnapMirror relationship.

=== Performance validation with YCSB

Yahoo! Cloud Serving Benchmark (YCSB) is a framework and a common set of workloads for evaluating the performance of different key-value and cloud serving stores. It has two components:

* The YCSB client, an extensible workload generator.
* The core workloads, a set of workload scenarios that the generator runs.

We chose workloads A, B, C, and a customized C from the six core workloads:

* *Workload A* is an update-heavy workload with a 50/50 mix of reads and writes. An example application is a session store that records recent actions.
* *Workload B* is a read-mostly workload with a 95/5 mix of reads and writes. An example application is photo tagging, where adding a tag is an update but most operations read tags.
* *Workload C* is a read-only workload with 100% reads. An example application is a user profile cache, where profiles are constructed elsewhere, such as in Hadoop deployments.
* *Workload customized C* is a read-only workload that we created because YCSB is intended mainly to test database performance and is not designed to stress the database I/O layer. It shows the throughput and response time you can expect from an AFF-A30 when application I/O requests load it heavily.

In our validation, the database held 700GB of data. Each document is 1,000 bytes in size and has 10 fields. The YCSB tool loaded the data.

=== Inline efficiency

NetApp deduplication and compression are inline storage efficiency technologies that increase the effective capacity of SSDs and reduce the effective cost per gigabyte. Inline storage efficiencies can also improve system performance because fewer physical blocks are written to store a given amount of logical data. Inline deduplication and inline compression are two key components of NetApp AFF that let you store the maximum amount of data at the lowest possible cost. These complementary technologies work together to achieve optimal savings.

==== Deduplication

Deduplication reduces storage capacity requirements by eliminating redundant blocks of data, as the following figure illustrates. NetApp deduplication improves storage efficiency by locating identical 4K blocks of data in a NetApp FlexVol volume and replacing the identical blocks with references to a single shared block. Before it removes the blocks, it performs a byte-level verification check to confirm that the blocks are identical. This check prevents potential problems related to hash collisions.

.Reducing storage capacity requirements through deduplication
image:mongodb-ontap-022.png[Diagram showing identical blocks replaced by references to a single shared block.]

NetApp AFF systems support deduplication as both an inline and a postprocess operation. As writes enter the system, inline deduplication eliminates duplicate blocks held in memory, which reduces the space needed to store the data.

If postprocess deduplication is enabled, it reclaims additional space by scanning existing data for duplicates and eliminating them. By default, AFF systems enable both inline deduplication and inline zero-block deduplication. Inline zero-block deduplication detects zero blocks inline and deduplicates them before they are written to disk.

==== Compression

NetApp compression provides transparent data compression at the file level. It does not compress the entire file as a single contiguous stream of bytes, because that would make it prohibitively expensive to service small reads or overwrites on part of a file. The entire file would have to be read from disk and uncompressed before the request could be served, which is especially burdensome for large files.

To avoid this problem, NetApp data compression compresses a small group of consecutive blocks, known as a compression group. When a read or overwrite request arrives, only that small group of blocks must be read, not the entire file. This approach optimizes read and overwrite performance and allows greater scalability in the size of the compressed files.

NetApp supports two types of compression:

* Adaptive compression (8K compression group size)
* Secondary compression (32K compression group size)

Adaptive compression is better suited to workloads that consist mainly of random writes or a mix of sequential and random writes. Secondary compression is better suited to workloads that consist mostly of large sequential I/Os (32K or larger).

Compression is supported only as an inline operation on AFF systems, and adaptive inline compression is enabled by default for all new volumes on AFF systems. If both compression and deduplication are enabled, compression runs first, followed by deduplication. You can enable or disable both at the FlexVol volume level.

The results in the first of the following figures show the storage efficiency statistics of MongoDB running the `mongoperf` workload on All Flash FAS controllers. The second figure indicates a data reduction ratio of greater than 15:1 with both inline deduplication and inline compression.

=== Serving NetApp Digital Advisor (AIQ) from MongoDB Atlas

==== Overview

NetApp Digital Advisor turns AutoSupport telemetry from ONTAP, E-Series, and StorageGRID systems into risks, capacity forecasts, and upgrade advice. NetApp serves that information to customers, partners, and NetApp staff from a MongoDB Atlas database on AWS. Heavy analytics stay on-premises. Prepared results are copied into Atlas, and an API layer reads them with access rules applied to every query.

==== Problem and requirements

.Challenges and requirements for serving Digital Advisor from MongoDB Atlas
[cols="31%,35%,34%",options="header"]
|===
|Challenge |Requirement |Value to the customer
|*Latency.* Analytics stores are built for batch work, so nothing on the request path may depend on them. |*Fast reads.* Join systems, clusters, volumes, and risks in one round trip. |Dashboards load without waiting on analytics.
|*Many data sources.* Dozens of feeds describe one system, on different schedules. |*Many writers, one document.* Each job updates only its own fields. |Each source refreshes on its own schedule.
|*Access control.* Customers, partners, and staff must each see only their own scope. |*Entitlement on every query,* built into query construction. |Each audience sees the right data.
|*User state.* Acknowledgements and preferences exist only in the serving store. |*Durability.* Majority writes, backups, and point-in-time recovery. |An action made today survives a failover.
|===

==== Solution

.AIQ serving-layer architecture
image:mongodb-ontap-025.png[Architecture of the Digital Advisor serving layer on MongoDB Atlas, from AutoSupport telemetry through the on-premises data lake and refresh jobs to the Atlas collections and API layer.]

The data flows through the following steps:

. Installed systems upload AutoSupport telemetry to NetApp.
. The data is prepared in an on-premises data lake and exposed as virtual datasets.
. Scheduled refresh jobs read one dataset each and bulk-upsert into one Atlas collection with majority write concern.
. An API layer on AWS reads Atlas, adds the access filter to every query, and serves Digital Advisor users.
. A separate authorizer service reads only the role, user, and token collections to build the user profile.

Three planes keep ownership clear:

* The *control plane* is one reviewed code repository that defines validators, indexes, and views.
* The *write plane* fills the database, and each writer sets only the fields it owns.
* The *read plane* serves the data and enforces access rules.

Every collection uses the same document envelope: keys, configuration attributes (including access fields), parent references for joins, and source metadata. Most collections are projections that the refresh jobs can rebuild. A smaller set is user state that exists only in Atlas.

==== Benefits to the customer

.Benefits for people using Digital Advisor
[cols="26%,74%",options="header"]
|===
|Benefit |What changes for the person using Digital Advisor
|*Speed* |Pages read pre-built documents, so response time does not depend on analytic load.
|*Trust* |Access fields sit on each document, so each audience gets a scoped view.
|*Quality* |Strict schema validation keeps bad records away from customer screens.
|*Continuity* |Acknowledgements and mitigations persist when a node fails.
|*Freshness* |A slow feed never holds back capacity or risk data.
|===

==== NetApp values in this design

* *Customer insight first.* Every design choice serves the screen that shows a customer's risks, capacity, and upgrade advice.
* *Data protection and stewardship.* Workloads have their own identities, and access fields are required on every document.
* *Trusted, governed data.* Schema changes need both reader and writer review and run through automation, not by hand.
* *Hybrid cloud by design.* Analytics stay on-premises next to the data, and the serving layer runs in the cloud.

==== Best practices

* *Deploy in order: validator, writer, reader.* Add a field to the validator before any writer sends it.
* *Backfill before requiring a field.* Making a field required breaks updates to documents that lack it.
* *Declare every index in code.* Indexes added by hand can be dropped by the next deployment.
* *Set only the leaf paths you own.* Setting a parent object erases fields that other jobs own.
* *Upsert on the fields of a unique index,* and use `$set` for the rest.
* *Use majority and retryable writes* for every writer.
* *Do not let a rejected write look like success.* Fail the job above a threshold and alert on rejections.
* *Read your own writes* from the primary or a causally consistent session when a user must see an action immediately.
* *Page by key, not by offset,* and project only the fields you need.
* *Back up what cannot be rebuilt,* confirm that point-in-time recovery covers user state, and test a single-collection restore.
* *Give each writer least privilege,* and tag every client with an application name.
* *Choose a lifecycle for every collection:* TTL, stale removal, or none with a stated reason.

*Deploy.* The Enterprise Operator watches for a replica-set manifest and creates the members. A project configuration and a credentials secret connect them to Ops Manager.

*Backup.* Ops Manager picks the snapshot node. The backup agent opens a `$backupCursor`, copies the data files, and sends them to Ops Manager. Ops Manager writes them to the blockstore, the S3 store, or the file system store.

*Restore.* The user requests a snapshot link, and Ops Manager creates a restore job. The snapshot streams from the store to the target server. A restore utility starts a temporary database, fetches the oplog, and applies it to the snapshot.

*Application consistency.* WiredTiger writes a journal, so a Snapshot copy of a volume that holds the data files and the journal together is crash-consistent, and `mongod` recovers it on start. If they sit on different volumes, take the Snapshot copies as one consistency group, or quiesce the database with `fsyncLock` first and release it afterward. See <<Appendix: Quiesce and balancer commands>> for the commands that you can adapt as pre-commands and post-commands.

*Where to snapshot.* Run the SnapCenter backup against a hidden secondary member (priority 0), so that the Snapshot copy does not compete with application traffic. Schedule it so that it does not overlap with the Ops Manager backup on the same member.

*Backup.* SnapCenter or Snap Creator runs the pre-command, if one is needed, and takes a Snapshot copy of the data and journal volumes according to policy. It then runs the post-command and starts a SnapMirror update to the second site or ONTAP in the cloud. Ops Manager continues its own backup of the replica set and the oplog.

*Restore.* Stop `mongod` on the target member, and use SnapRestore to restore its volume from the chosen Snapshot copy. You can also mount a FlexClone volume first to inspect the data. Start `mongod`, and let the member rejoin the replica set. For point-in-time recovery, restore the Snapshot copy to a standalone server and apply the oplog from Ops Manager up to the chosen time. If the Snapshot copy is older than the oplog window, the member needs an initial sync from the primary.

*Recovery order.* Try the options in this order: SnapRestore of a member volume (fastest), Ops Manager point-in-time restore (most precise), and SnapMirror failover to the second site (site loss).

*Recovery objectives.* The Snapshot schedule sets the recovery point of a SnapRestore. The oplog sets it for an Ops Manager point-in-time restore. SnapRestore avoids copying data, whereas an Ops Manager restore streams the snapshot, so the recovery times differ. This report gives no measured values, so measure both paths on your own data.

*Constraints.* Confirm that a MongoDB plug-in is available for your SnapCenter version, as described in <<NetApp SnapCenter and Snap Creator Framework>>. If it is not, script the same operations through the ONTAP REST API. SnapCenter does not protect Kubernetes persistent volumes directly. Use NetApp Trident protect for those, and keep Ops Manager as the backup path for them.

==== NetApp values in this design

* *Protection first.* Ops Manager backup and restore are built in from the first manifest, and SnapCenter adds storage-level Snapshot copies underneath.
* *Choice of storage.* Ops Manager snapshots can land on StorageGRID over S3 or on an ONTAP NFS volume, which SnapCenter can also protect.
* *Trusted operations.* Credentials sit in a Kubernetes secret, and every change is declared in code.
* *Hybrid by design.* The same pattern works on OpenShift, Kubernetes, and VMs, on-premises or in the cloud.
* *Fast recovery and cloning.* SnapRestore returns a member volume from a Snapshot copy without streaming the data, and FlexClone creates dev/test copies without copying it. Snap Creator validated this workflow in this report.
* *Disaster recovery.* SnapMirror replicates the Snapshot copies to a second site or to ONTAP in the cloud, as validated in this report with Snap Creator.

==== Best practices

* *Keep every manifest in version control,* and change the version field to upgrade.
* *Run three members* for each replica set, including the Ops Manager application and backup databases.
* *Store the API key in a secret* and grant only the access it needs.
* *Choose the snapshot store by recovery need,* then size it for retention.
* *Keep the oplog store healthy,* because point-in-time recovery needs it.
* *Alert on stale snapshots* by using Ops Manager monitoring.
* *Practice the restore on a schedule* and time it.
* *Limit who can request snapshot links,* and check free space on the target server first.
* *Automate through the REST API* with audit logging, and keep Ops Manager and agents on supported versions.
* Start with pattern A, and move to pattern C after you have rehearsed the restore.
* Take the SnapCenter Snapshot copies from a hidden secondary member, and keep them outside the Ops Manager backup window.
* Put the data files and the journal on one volume, or quiesce the database with `fsyncLock` before the Snapshot copy and release it afterward.
* Keep Snapshot copies recent enough to fall within the replica-set oplog window. Otherwise, the restored member needs an initial sync.
* Test SnapMirror failover to the second site on a schedule, and record how long each recovery path takes.
* Confirm SnapCenter plug-in support for your MongoDB version before you rely on it, and keep ONTAP REST API scripts as a fallback.

== Summary

This reference architecture provides an end-to-end solution for efficiently deploying a virtualized, scale-out MongoDB NoSQL database on NetApp intelligent data infrastructure. In the tested architecture, which combined NetApp storage technology with VMware vSphere, the MongoDB VMs and databases were hosted on a scale-out NetApp AFF array. We created backups with Snap Creator and handled disaster recovery with NetApp ONTAP software-defined storage in AWS.

This solution validated the following key benefits:

* Predictable, high performance with consistently low latency, which gives the most demanding MongoDB-based analytics applications very fast response times.
* Inline deduplication and compression that make MongoDB on flash storage cost efficient.
* Instant, space-efficient database cloning that speeds the setup of dev/test and QA environments without requiring new storage.
* Backup and recovery based on space-efficient NetApp Snapshot copies and remote replication to the cloud.

Beyond the validation results, NetApp AFF complements MongoDB with the following key capabilities:

* A scale-up and scale-out all-flash array that lets storage scale modularly with MongoDB.
* Nondisruptive operations that deliver maximum uptime and high availability.

In YCSB performance testing, NetApp AFF delivered excellent results, demonstrating a high-performance, cost-effective all-flash array for scaling out MongoDB deployments.

This report also describes two customer use cases: serving Digital Advisor from MongoDB Atlas, and enterprise backup and recovery with MongoDB Ops Manager. For Ops Manager, it gives design guidance, still to be evaluated, on adding NetApp SnapCenter for storage-level Snapshot copies, fast recovery, and disaster recovery.

----
[mongodb@mdb-ms-1 ~]$ mongo mdb-srv-1:27018/admin
> var cfg = { _id: "shard1", members: [ { _id: 0, host: "mdb-srv-1:27018" }, { _id: 1, host: "mdb-srv-10:27018" }, { _id: 2, host: "mdb-srv-11:27018" } ] };
> rs.initiate(cfg);
----
. Check the replica set status from the shard member:
+
----
[mongodb@mdb-srv-1 ~]$ mongo --host mdb-srv-1 --port 27018
shard1:PRIMARY> rs.printReplicationInfo()
PRIMARY> rs.status()
----
. Add the first shard from the application server. If you add the same shard again from another application server, MongoDB reports that the shard already exists:
+
----
[mongodb@mdb-ms-1 ~]$ mongo mdb-ms-1:27017/admin
mongos> db.adminCommand( { addShard : "shard1/mdb-srv-1:27018,mdb-srv-10:27018,mdb-srv-11:27018" } )
----
. Check the sharding status:
+
----
mongos> sh.status();
----
. Add the second shard. Prepare `mdb-srv-2`, `mdb-srv-20`, and `mdb-srv-21` the same way as the first shard, initiate its replica set, and add it:
+
----
mongos> db.adminCommand( { addShard : "shard2/mdb-srv-2:27018,mdb-srv-20:27018,mdb-srv-21:27018" } )
----
. Run `sh.status()` again to confirm that both shards (`shard1` and `shard2`) are listed. The databases that you load are then spread across the sharded cluster.
